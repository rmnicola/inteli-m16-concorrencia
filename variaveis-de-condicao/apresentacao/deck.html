O pai espera o filho

volatile int done = 0;void *child(void *arg) {
    printf("child\n");
    done = 1;
    return NULL;
}int main(int argc, char *argv[]) {
    printf("parent: begin\n");
    pthread_t c;
    Pthread_create(&c, NULL, child, NULL); // child
    while (done == 0)
        ; // spin
    printf("parent: end\n");
    return 0;
}

Funciona, mas o pai gira: queima CPU só esperando.

Introdução do cap. 30, figs. 30.1 e 30.2. Locks não bastam: às vezes uma thread precisa esperar uma condição. Aqui, o pai espera o filho terminar (um join feito à mão); a saída desejada é parent: begin, child, parent: end. Bloco 1: a variável compartilhada done. Bloco 2: o filho marca done = 1 ao terminar. Bloco 3: o pai cria o filho e gira até done virar 1. Avance: funciona, mas é muito ineficiente, e em alguns casos pode até ser incorreto. O que queremos: pôr o pai para dormir até a condição ser verdadeira. Como esperar por uma condição?

wait e signal

pthread_cond_wait(pthread_cond_t *c, pthread_mutex_t *m);
pthread_cond_signal(pthread_cond_t *c);

A variável de condição: uma fila onde a thread dorme.

O lock, já preso: wait solta o lock e dorme, de forma atômica, e pega o lock de novo antes de voltar.

Acorda uma das threads que dormem nessa fila.

Seção 30.1. Uma variável de condição é uma fila explícita onde as threads se colocam quando o estado não é o desejado (esperando pela condição); outra thread, quando muda esse estado, acorda uma delas (sinalizando a condição). A ideia vem dos "private semaphores" de Dijkstra; o nome vem de Hoare, nos monitores. Declara-se com pthread_cond_t c e precisa ser inicializada. Passo 1: c é a fila. Passo 2: m é o mutex, que precisa estar preso na chamada; o wait o solta ao pôr a thread para dormir, de forma atômica, e o readquire antes de retornar. Essa complexidade existe para evitar corridas na hora de dormir (vamos ver uma daqui a pouco). Passo 3: signal acorda uma thread que dorme em c; se não houver nenhuma, não faz nada. Daqui em diante, wait() e signal() para encurtar.

Dormir numa variável de condição

fila de c

Animação do wait e do signal (o lock fica implícito: quem chama wait ou signal o segura). Cada faixa é uma thread; a roxa é a que está na CPU, e a janela mostra o que ela executa. À direita, a fila da variável de condição c. T1, T2 e T3 rodam, uma de cada vez, chamam wait e vão dormir na fila: o escalonador não as escolhe mais. T4 roda e chama signal: uma thread da fila, qualquer uma (aqui sorteada quando o deck abre), acorda e passa a PRONTA, mas não roda na hora; só quando o escalonador a escolhe ela volta do wait (com o lock). Cada signal acorda no máximo uma. Neste exemplo, quem acorda também sinaliza, e acorda a próxima. Quem sinaliza pode ser qualquer thread que esteja rodando; T4 poderia chamar signal três vezes e acordar as três, uma por chamada. A última sinaliza com a fila vazia: nada acontece, e o sinal não fica guardado para quem chegar depois (é o problema do exemplo sem done).

Esperar sem girar

int done = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t c = PTHREAD_COND_INITIALIZER;void thr_exit() {
    Pthread_mutex_lock(&m);
    done = 1;
    Pthread_cond_signal(&c);
    Pthread_mutex_unlock(&m);
}void thr_join() {
    Pthread_mutex_lock(&m);
    while (done == 0)
        Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}

Estado, lock e variável de condição.

O filho chama ao terminar: muda o estado e sinaliza, com o lock.

O pai chama para esperar: dorme enquanto done == 0.

Fig. 30.3. O filho chama thr_exit() depois de imprimir "child"; o main cria o filho e chama thr_join(). Bloco 1: as três peças que andam sempre juntas: a variável de estado done, o lock m e a variável de condição c. Bloco 2: thr_exit pega o lock, põe done = 1, sinaliza e solta. Bloco 3: thr_join pega o lock e, enquanto done for 0, dorme no wait (que solta o lock). Dois casos. (1) O pai roda primeiro (uma CPU): pega o lock, vê done == 0 e dorme, soltando o lock; o filho roda, imprime, pega o lock, põe done = 1 e sinaliza; o pai volta do wait com o lock, sai do laço, solta e imprime "parent: end". (2) O filho roda primeiro: põe done = 1 e sinaliza para ninguém; o pai chega, vê done == 1 e nem dorme. Por que while e não if? Aqui parece desnecessário, mas é sempre boa ideia; vamos ver por quê.

A mesma ideia, sem o lock.

O pai vê done == 0 e é interrompido antes do wait.

O filho põe done = 1 e sinaliza para ninguém.

O pai volta e dorme para sempre.

condição de corrida

Fig. 30.5. Por que o wait recebe o lock? Esta versão não usa lock nenhum (não é código real: o pthread_cond_wait sempre exige o mutex; o capítulo finge que não, só para o contraexemplo). Bloco 1: o filho muda done e sinaliza. Bloco 2: o pai testa done e dorme. Avance: o pai vê done == 0 e vai dormir, mas é interrompido entre o teste e o wait. Avance: o filho roda, põe done = 1 e sinaliza; ninguém está na fila, ninguém acorda. Avance: o pai volta, chama wait e dorme para sempre. É a mesma corrida entre testar e agir do lock com flag simples: o teste de done e o ato de dormir precisam ser atômicos, e é por isso que o wait solta o lock e dorme numa operação só. Quadro "Always hold the lock while signaling": segure o lock no signal e no wait, e você estará sempre seguro.

Fig. 30.4. E por que a variável done, e o while em volta do wait? Esta versão tem o lock, mas não tem estado: o pai dorme sempre, sem testar nada. Bloco 1: o filho só sinaliza. Bloco 2: o pai só espera. Avance: o filho roda logo depois de criado e sinaliza; não há thread dormindo em c, e o sinal se perde. Avance: o pai chega, chama wait e fica preso; nenhuma thread vai acordá-lo. A variável de condição não tem memória; quem guarda o que aconteceu é done. Dormir, acordar e travar giram em torno dessa variável de estado: o pai só dorme se done == 0. Daí as três peças da fig. 30.3: estado, lock e variável de condição, sempre juntos.

Produtor/consumidor

⋮

Seção 30.2. Antes do código, a estrutura: um buffer limitado entre produtores, que geram itens e os põem no buffer, e consumidores, que os tiram e usam. Exemplos reais: a fila de requisições de um servidor web com várias threads (o produtor põe requisições HTTP, as threads consumidoras as tiram e processam) e o pipe em grep foo file.txt | wc -l (grep produz, wc consome, e o buffer limitado fica no kernel). O problema foi proposto por Dijkstra, e foi ele que o levou a inventar o semáforo (próximo deck). Com as setas, o slide roda um roteiro com MAX = 1: o produtor põe até dormir, o consumidor tira e o acorda, o consumidor tira até dormir, e o produtor põe e o acorda. Depois, livre: clique no produtor para pôr um item, no consumidor para tirar um. Buffer cheio: o produtor dorme até um consumidor tirar algo e acordá-lo; buffer vazio: o consumidor dorme até o produtor pôr algo. Arraste a alça coral para mudar MAX (de 1 a 8): o ↺ volta ao início (MAX = 1, buffer vazio). fill aponta onde o próximo item entra; use, de onde o próximo sai, dando a volta no fim (buffer circular). O buffer é compartilhado: put e get mexem nele e em count, e por isso precisam de exclusão mútua; e cada lado precisa esperar uma condição (não cheio, não vazio).

put e get, sem sincronização

int buffer;
int count = 0; // initially, emptyvoid put(int value) {
    assert(count == 0);

}int get() {
    assert(count == 1);

void *producer(void *arg) {
    int i;
    int loops = (int) arg;
    for (i = 0; i < loops; i++) {
        put(i);
    }
}void *consumer(void *arg) {

        int tmp = get();
        printf("%d\n", tmp);
    }

Um buffer de uma posição; count diz se está cheio.

put só funciona com o buffer vazio.

get só funciona com o buffer cheio.

O produtor põe loops itens.

O consumidor tira para sempre.

Duas threads mexem em buffer e count.

E ninguém espera: put num buffer cheio dispara o assert.

seção crítica

Figs. 30.6 e 30.7. O buffer mais simples: um inteiro só (poderia ser um ponteiro para uma estrutura) e count, que diz se está cheio. Bloco 1: as variáveis. Blocos 2 e 3: put() supõe o buffer vazio (o assert confere), guarda o valor e marca cheio; get() faz o contrário. Depois o buffer vira uma fila com várias posições, como no simulador. Blocos 4 e 5: o produtor põe loops inteiros; o consumidor tira para sempre e imprime. Avance: put e get leem e escrevem buffer e count, que são compartilhados: seção crítica, e sem lock dá condição de corrida. Avance: e mais que exclusão mútua, cada lado precisa esperar: só pôr com count == 0, só tirar com count == 1. Se o produtor puser num buffer cheio ou o consumidor tirar de um vazio, o assert dispara. Pôr um lock em volta não basta; precisamos de variáveis de condição.

semântica Mesa

Fig. 30.9, o código com if e uma CV. Dois consumidores (Tc1, Tc2) e um produtor (Tp); o escalonador decide quem vai para a CPU. Avance a cada passo. Tc1 pega o lock, vê o buffer vazio (c1, c2) e dorme em cond (c3), soltando o lock. Tp roda, enche o buffer (p1, p2, p4) e sinaliza (p5): Tc1 sai da fila de cond e vai para as prontas, mas não roda ainda. Tp volta ao laço, vê o buffer cheio e dorme (p6, p1–p3). Agora o escalonador escolhe Tc2, que entra na frente: o buffer está cheio, então ele nem dorme (c1, c2, c4) e consome o único valor; sinaliza (c5) e acorda Tp. Por fim Tc1 roda: readquire o lock ao voltar do wait, não testa de novo (é um if) e chama get() com o buffer vazio: o assert dispara. O sinal só acorda a thread; é uma dica de que o estado mudou, sem garantia de que continue assim quando ela rodar. Essa é a semântica Mesa (Lampson e Redell), a de praticamente todo sistema. A semântica Hoare garante que a thread acordada roda na hora, mas é mais difícil de construir.

Acordou? Testa de novo. Se o buffer estiver vazio, volta a dormir.

Ainda falha: com uma CV só, quem sinaliza não escolhe quem acorda.

Fig. 30.10. O mesmo código, com while no lugar de if, no consumidor (c2) e no produtor (p2). Avance: agora Tc1 acorda e, com o lock preso, testa count de novo; se Tc2 já consumiu, volta a dormir. Fig. 30.11, com o código do while e uma CV. Avance a cada passo. Os dois consumidores rodam primeiro e dormem (c1–c3: nada para pegar). Tp enche o buffer e acorda um consumidor, Tc1, que vai para as prontas. Tp volta ao laço (soltando e pegando o lock), vê o buffer cheio e dorme. Agora Tc1 está pronta e Tc2 e Tp dormem. Deveria ser o produtor, porque o buffer esvaziou; mas pode ser Tc2, dependendo de como a fila de espera é gerenciada. Tc1 volta ao laço, vê o buffer vazio e dorme. O sinal precisa ter direção: consumidor só acorda produtor, e vice-versa.

Fig. 30.12. Duas variáveis de condição, cond_t empty, fill. Avance: o produtor dorme em empty (espera o buffer esvaziar) e, depois de pôr, sinaliza fill. Quadro "Use while (not if) for conditions": o while também cobre os despertares espúrios (spurious wakeups), em que, por detalhe de implementação, duas threads acordam com um signal só.

Um buffer com MAX posições

int buffer[MAX];
int fill_ptr = 0;
int use_ptr = 0;
int count    = 0;void put(int value) {
    buffer[fill_ptr] = value;
    fill_ptr = (fill_ptr + 1) % MAX;
    count++;
}int get() {
    int tmp = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % MAX;
    count--;
    return tmp;
}
void *producer(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        Pthread_mutex_lock(&mutex);
        while (count == MAX)
            Pthread_cond_wait(&empty, &mutex);
        put(i);
        Pthread_cond_signal(&fill);
        Pthread_mutex_unlock(&mutex);
    }
}

O buffer vira uma fila circular: fill_ptr e use_ptr, como no simulador.

put escreve em fill_ptr e avança.

get lê em use_ptr e avança.

A sincronização é a mesma: duas CVs e while.

Só muda a condição: o produtor dorme só com todas as posições cheias.

Figs. 30.13 e 30.14, a solução correta. Mais posições no buffer permitem produzir vários valores antes de dormir e consumir vários antes de dormir: com um produtor e um consumidor, menos trocas de contexto; com vários, produção e consumo concorrentes. Bloco 1: o vetor, os dois índices e count. Bloco 2: put grava em fill_ptr e avança com módulo MAX. Bloco 3: get lê em use_ptr e avança. Bloco 4: o produtor, igual ao de duas CVs. Avance: a única mudança é a condição: o produtor dorme só se count == MAX (p2); o consumidor continua dormindo só se count == 0 (c2). Voltar ao simulador se quiser mostrar com MAX maior.

O exemplo da seção 30.3. Nenhum byte livre. Ta chama allocate(100) e Tb chama allocate(10): as duas dormem na mesma variável de condição. Avance: Tc chama free(50); agora há 50 bytes. Avance: o signal acorda uma thread só, e pode ser Ta. Avance: Ta testa de novo (while), 50 < 100, e volta a dormir. Tb, que só precisava de 10, continua dormindo: ninguém progride. Quem sinaliza não sabe quem acordar. Avance: a solução de Lampson e Redell é trocar pthread_cond_signal por pthread_cond_broadcast, que acorda todas as threads que esperam. Avance: cada uma testa de novo: Ta volta a dormir, Tb aloca 10 e sobram 40. O custo: acordar threads à toa, que só testam e voltam a dormir. Lampson e Redell chamam isso de covering condition, porque cobre todos os casos em que alguém precisa acordar, de forma conservadora. Daria para usar broadcast no produtor/consumidor de uma CV só, mas lá havia solução melhor (duas CVs). Se o programa só funciona trocando signal por broadcast, sem você achar que precisaria, provavelmente há um bug.
