Um flag na memória

void lock(lock_t *m) {
    while (m->flag == 1)
        ;            // gira
    m->flag = 1;
}

void unlock(lock_t *m) {
    m->flag = 0;
}

Testar e escrever: duas operações. E se a troca de contexto cair no meio?

Fig. 28.1, a primeira tentativa: uma variável flag. lock() espera girando enquanto o flag é 1 e depois escreve 1; unlock() escreve 0. Avance: testar e escrever são duas operações separadas. No próximo slide, eles são o escalonador e tentam quebrar esse lock.
Fig. 28.2 do OSTEP. Vocês são o escalonador: o botão de cada thread roda a próxima linha dela, e cada thread repete sem parar (pega o lock, lê count, escreve count + 1, libera). Primeiro uma passada inteira de T1 e depois T2: tudo certo. Depois peça a menor sequência que põe as duas com o lock: T1 testa (flag = 0), T2 testa (ainda 0), as duas escrevem 1 e entram. O aviso aparece embaixo. Continue as duas até escreverem count: um incremento se perde. Termo: não há exclusão mútua. Ainda: a espera girando (spin-waiting) gasta CPU sem fazer nada.

Que sequência de passos quebrou o flag?

Falta uma operação atômica. 3: seção 28.4: exclusão mútua (correção), justiça (ninguém espera para sempre) e desempenho (sem disputa, com disputa numa CPU, com disputa em várias). o que cada instrução atômica faz, se dá para uma thread nunca pegar o lock, e quanto se gira

15 minutos. A leitura vai de desligar as interrupções (28.5) ao fetch-and-add e ao ticket lock (28.11). Nos simuladores: tentar a sequência que quebrou o flag (não dá), e, com 3 threads, fazer uma delas nunca pegar o lock no test-and-set (dá) e no ticket (não dá).

Desligar as interrupções

void lock() {
    DisableInterrupts();
}

void unlock() {
    EnableInterrupts();
}

Com uma CPU, nada interrompe a seção crítica.

Com várias CPUs, as outras continuam rodando.

E um aplicativo não pode desligar interrupções.

Seção 28.5, a primeira solução, dos sistemas de um processador só. Sem interrupção não há troca de contexto, e a seção crítica roda inteira. Avance: com várias CPUs, desligar as interrupções numa não impede as outras de entrar. Avance: é uma operação privilegiada; se um aplicativo pudesse, poderia chamar lock() no começo e monopolizar a máquina. Ainda: interrupções perdidas (um disco que terminou uma leitura) e o custo nas CPUs modernas. O SO usa isso dentro do kernel, em trechos curtos.

Test-and-set

int TestAndSet(int *p, int novo) {
    int velho = *p;
    *p = novo;
    return velho;
}   // tudo de uma vez, atômico

void lock(lock_t *m) {
    while (TestAndSet(&m->flag, 1) == 1)
        ;   // gira
}

O hardware lê o valor antigo e escreve o novo numa instrução só.

Veio 0: o lock estava livre, e agora é meu. Veio 1: tento de novo.

Seção 28.7, fig. 28.3. O test-and-set (no x86, xchg) devolve o valor antigo e grava o novo, atomicamente. Passo 2: se voltou 0, o lock estava livre e eu o peguei (o 1 já está lá); se voltou 1, estava ocupado, e escrever 1 de novo não muda nada. unlock() continua escrevendo 0. É o spin lock. Atenção: numa CPU só, ele precisa de um escalonador preemptivo, senão quem gira nunca solta a CPU.
O mesmo simulador com test-and-set: TAS(&flag) devolve o flag antigo e escreve 1 numa linha só. Peça de novo a sequência que quebrou o flag: não existe, porque não há como cair entre o teste e a escrita. Depois passe para 3 threads e peça para fazer uma delas nunca pegar o lock: basta escalonar T3 só quando o lock está ocupado. Dá para fazer isso para sempre: o spin lock não é justo. E repare no contador "girou": tempo de CPU jogado fora.

Outras instruções atômicas

test-and-set 
velho = *p; *p = novo;
compare-and-swap 
if (*p == esperado) *p = novo;
load-linked e store-conditional 
v = LL(p); SC(p, novo);
fetch-and-add 
velho = *p; *p = velho + 1;
Seções 28.9 a 28.11. Todas fazem leitura e escrita numa operação indivisível. Compare-and-swap (x86: cmpxchg) só escreve se o valor ainda é o esperado e devolve o que achou; com ele dá para fazer o mesmo spin lock, e mais coisas (estruturas sem lock). Load-linked e store-conditional (ARM, RISC-V, PowerPC): o SC só grava se ninguém escreveu em p desde o LL, e diz se conseguiu. Fetch-and-add incrementa e devolve o valor antigo: com ele vem o ticket lock, o próximo slide.

Ticket lock

void lock(lock_t *l) {
    int eu = FetchAndAdd(&l->ticket);
    while (l->turn != eu)
        ;   // gira
}

void unlock(lock_t *l) {
    l->turn = l->turn + 1;
}

Pega uma senha.

Espera a sua vez.

Chama a próxima senha.

Seção 28.11, fig. 28.7, de Mellor-Crummey e Scott. Como a fila de senhas da padaria: fetch-and-add dá a cada thread um número diferente (ticket), e turn diz de quem é a vez. unlock() chama o próximo número. Toda thread que pegou um número vai entrar, na ordem: é justo.
O mesmo simulador com o ticket lock (FAA = fetch-and-add). Com 3 threads, peça de novo para T3 nunca entrar: depois que ela pega um número, as outras não conseguem passar na frente dela. Quem decide a ordem é a ordem dos números, não a sorte do escalonamento. Mas o contador "girou" continua subindo: a espera ainda é ocupada.

Discussão

Por que desligar as interrupções não serve?

O que muda com uma instrução atômica?

Dá para uma thread nunca pegar o lock?

10 minutos. 1: só vale com uma CPU, e um aplicativo não pode desligar interrupções. 2: teste e escrita numa operação só (test-and-set, compare-and-swap, LL/SC, fetch-and-add): o spin lock é correto. 3: no test-and-set, sim (não é justo); no ticket lock, não: cada thread entra na vez do seu número. Mas os dois giram enquanto esperam. Depois, as questões 2 e 3, e o placar.

Placar

Test-and-set: correto, não é justo, gira (numa CPU, um quantum inteiro por thread esperando). Ticket: correto e justo, mas gira do mesmo jeito. O que fazer enquanto espera é o bloco 3.

mexa

o slide Girando à toa: girar, yield e fila, com 1 e 2 CPUs

anote

quanto da CPU se perde girando com 2, 4 e 8 threads, e o que o yield e a fila resolvem

12 minutos. A leitura vai do problema de girar demais (28.12) ao yield, às filas com park e unpark, ao futex do Linux e ao lock em duas fases. No simulador: com 1 CPU, o coral cresce com as threads; o yield troca o giro por trocas de contexto; a fila é justa (a ordem fica 1 2 3 4 …). Com 2 CPUs e 2 threads, girar quase não desperdiça.
Seções 28.12 a 28.14. N threads repetem: trabalham fora do lock, pegam o lock, ficam 3 unidades na seção crítica, liberam. Rodízio com quantum de 6 unidades, troca de contexto de 1. Comece com 1 CPU e girar: aumente as threads e veja o coral crescer. Quando a dona perde a CPU na seção crítica, as outras giram o quantum inteiro. Troque para yield (28.13): quem encontra o lock ocupado cede a CPU; o coral quase some, mas as trocas de contexto crescem com o número de threads, e ainda não há garantia de quem pega o lock. Troque para fila (28.14): quem encontra o lock ocupado dorme na fila do lock, e a dona acorda a próxima ao liberar; a ordem fica 1 2 3 4 1 2 3 4. Por fim 2 CPUs com 2 threads e girar: girar quase não desperdiça, porque a dona está rodando na outra CPU. Mas com 2 CPUs, 8 threads e girar, veja a ordem: T1 e T2 pegam o lock sempre.

Dormir em vez de girar

void lock(lock_t *m) {
    if (ocupado(m)) {
        queue_add(m->q, gettid());
        park();          // dorme
    }
}

void unlock(lock_t *m) {
    unpark(queue_remove(m->q));
}

Entra na fila do lock e pede ao SO para dormir.

Quem libera acorda a primeira da fila.

Seção 28.14, um esboço da fig. 28.9 (no Solaris: park e unpark). O SO dá as primitivas de dormir e acordar; o lock guarda a fila de quem espera. A thread acordada já recebe o lock, sem disputar de novo: por isso a fila é justa. O código real precisa de um guard (um spin lock curto) protegendo a fila e o flag, e de cuidado com a corrida entre park e unpark (setpark). Dormir custa duas trocas de contexto.

Lock em duas fases

gira um pouco
dorme na fila
fase 1fase 2, se não conseguiu

Se o lock vai ser liberado logo, girar sai mais barato que dormir.

futex no Linux

Seções 28.15 e 28.16. Girar só compensa quando a espera é curta, e dormir só compensa quando é longa. O lock em duas fases (Dahm, anos 1960) gira um pouco e, se não conseguir, dorme. É o que o mutex do Linux faz com o futex: um inteiro na memória, operações atômicas no caminho rápido (sem chamar o SO quando não há disputa) e futex_wait/futex_wake quando precisa dormir. O pthread_mutex_lock que usamos na aula passada é assim.

Discussão

Quanto da CPU se perde girando? Por quê?

O que o yield resolve, e o que não resolve?

Quando vale girar antes de dormir?

10 minutos. 1: quando a dona do lock perde a CPU na seção crítica, cada thread que espera gira um quantum inteiro: o desperdício cresce com o número de threads. 2: o yield devolve a CPU, mas cada espera custa uma troca de contexto por thread, e ninguém garante a ordem (justiça). A fila resolve as duas coisas, ao custo de dormir e acordar. 3: quando a espera é curta e há mais de uma CPU: o lock em duas fases, como o futex. Depois, as questões 4 e 5, e o placar completo.

Placar

O placar completo. Yield: tira o giro, mas paga trocas e não é justo. Fila: justa e sem giro, mas dormir e acordar custa caro quando a espera seria curta. Duas fases: o que se usa na prática (pthread_mutex no Linux).

Para pensar

Um lock justo é sempre mais rápido?

Quando girar é melhor que dormir?

E se a estrutura inteira tiver um lock só?

Fechamento. 1: não; o ticket lock é justo e gira tanto quanto o test-and-set, e a fila é justa mas paga trocas de contexto. 2: quando a espera é curta e há mais de uma CPU (a dona do lock está rodando); com uma CPU, ou com esperas longas, dormir.
