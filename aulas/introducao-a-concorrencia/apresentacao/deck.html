Até agora, um processo tinha um único ponto de execução: um PC de onde as instruções são buscadas. Avance: um programa multithread tem mais de um PC, cada um executando por conta própria, com os próprios registradores. Cada thread é quase um processo separado, com uma diferença: todas compartilham o mesmo address space, e por isso enxergam os mesmos dados (OSTEP, início do cap. 26).

Fig. 26.1 do OSTEP, um address space de 16 KB. À esquerda, o processo clássico: código e heap em cima, uma pilha embaixo, e os dois crescem um em direção ao outro. Avance: com duas threads, cada uma chama as próprias funções, então precisa da própria pilha. Variáveis locais, parâmetros e endereços de retorno ficam na pilha da thread (o livro chama isso de thread-local storage). O layout bonito acaba, mas pilhas costumam ser pequenas (a exceção é recursão pesada). Código, heap e globais continuam compartilhados.

Troca de contexto

Primeiro entre dois processos, depois entre duas threads. Processos (passos 0 a 2): A está na CPU; o SO salva os registradores de A no PCB (process control block) e restaura os de B. O PTBR (page-table base register) muda, porque B tem outro address space, e as traduções da TLB de A não servem para B: a TLB é esvaziada (ou cada entrada tem um identificador do processo, o ASID). Threads (passos 3 a 5): duas threads do mesmo processo. O SO salva T1 no TCB (thread control block) e restaura T2: PC, SP e eax mudam, o PTBR é o mesmo e a TLB continua valendo. Pergunta: qual das duas trocas é mais barata? Por quê?

Quem roda primeiro?

t0.c, fig. 26.2. A main cria T1 (imprime "A") e T2 (imprime "B") e espera as duas com join. Pergunta antes de avançar: o que esse programa imprime? Avance: uma execução, na ordem em que as threads foram criadas. Avance de novo: outra execução, com B antes de A (fig. 26.5). Por quê? Uma thread criada pode rodar na hora ou muito depois; quem decide é o escalonador, e ser criada primeiro não quer dizer rodar primeiro. "main: end" sempre sai por último, por causa dos joins.

Paralelização · uma thread por CPU

Primeiro motivo: paralelismo. Somar ou incrementar um vetor enorme numa CPU só: um pedaço depois do outro. Avance: com quatro CPUs e uma thread por CPU, cada uma faz um quarto, e o trabalho termina em um quarto do tempo (no caso ideal). Transformar um programa sequencial nisso é paralelizar. Pergunta: e com 8 threads em 4 CPUs?

Sobreposição de E/S e cálculo

Segundo motivo, mais sutil: não travar o programa numa E/S lenta (disco, rede, até uma falta de página). Enquanto T1 está bloqueada, o escalonador põe outra thread para rodar. Avance: T2 calcula durante a espera de T1, e ainda dispara a própria E/S. É a multiprogramação dentro de um programa só; servidores web e bancos de dados fazem isso o tempo todo.

Indeterminado

t1.c, fig. 26.6. Duas threads, cada uma soma 1 ao contador global 10 milhões de vezes. O esperado é 20 milhões. Pergunta: alguém aposta no resultado? Avance: às vezes dá certo, mas em geral não, mesmo numa CPU só. E avance de novo: cada execução dá um resultado diferente. O resultado é indeterminado. Por quê? A resposta está no que o compilador gera para uma linha só.

counter = counter + 1;

↓

100  mov 0x8049a1c, %eax   // lê da memória
105  add $0x1, %eax         // soma no registrador
108  mov %eax, 0x8049a1c   // escreve na memória
Seção 26.4. Uma linha de C, três instruções x86 (objdump -d mostra isso no seu binário). O counter está no endereço 0x8049a1c. A instrução mov copia o valor para o eax, o add soma 1 no registrador, o segundo mov grava de volta. Uma interrupção de timer pode cair entre quaisquer duas delas. No próximo slide, vocês são o escalonador.
Fig. 26.7 do OSTEP. O counter começa em 50; cada thread vai executar as três instruções uma vez; o certo é 52. A turma é o escalonador: o botão de cada thread (step over) roda a próxima instrução dela. Cada thread tem o próprio eax (salvo no TCB quando ela sai da CPU). Primeiro rode T1 inteira e depois T2: 52. Recomece (↺) e peça um escalonamento que dê errado, por exemplo o da fig. 26.7: T1 faz mov e add, troca, T2 faz as três, T1 grava 51. Termos que aparecem: race condition (o resultado depende do momento das trocas) e seção crítica (o trecho que acessa a variável compartilhada, a barra coral). O que queremos é exclusão mútua: enquanto uma thread está na seção crítica, a outra não entra. Pergunta: quantos escalonamentos dão 52? E quantos dão 51?

E se fosse uma instrução só?

memory-add 0x8049a1c, $0x1

Atômica: ou executa inteira, ou nada. A interrupção nunca cai no meio.

Seção 26.5, o desejo de atomicidade. Uma instrução hipotética que soma direto na memória, e que o hardware garante ser atômica ("tudo ou nada", como uma transação). Resolveria o contador, mas não dá para ter uma instrução atômica para cada estrutura de dados (uma árvore B, por exemplo). Em vez disso, o hardware dá umas poucas instruções úteis e, com a ajuda do SO, construímos primitivas de sincronização. É o assunto das próximas aulas. Hoje: as primitivas que a biblioteca de threads já oferece.

Criar uma thread

#include <pthread.h>

int pthread_create(pthread_t *thread,
                   const pthread_attr_t *attr,
                   void *(*start_routine)(void *),
                   void *arg);

Onde guardar a identificação da thread.

Atributos, como o tamanho da pilha. NULL: os padrões.

A função que a thread vai executar.

O argumento dessa função: void * aceita qualquer tipo.

Seção 27.1. Quatro argumentos, um por passo. O terceiro é um ponteiro para função: recebe um void * e devolve um void *. Por que void *? Porque assim a função pode receber qualquer argumento e devolver qualquer resultado: basta converter (cast). Para passar mais de um valor, empacote numa struct e passe o endereço dela (fig. 27.1).

Esperar a thread terminar

void *mythread(void *arg) {
    myret_t *r = Malloc(sizeof(myret_t));
    r->x = 1; r->y = 2;
    return (void *) r;
}

int main(int argc, char *argv[]) {
    pthread_t p;
    myret_t *r;
    Pthread_create(&p, NULL, mythread, NULL);
    Pthread_join(p, (void **) &r);
    printf("%d %d\n", r->x, r->y);
}

join bloqueia a main até a thread p terminar.

O valor devolvido pela thread chega pelo segundo argumento do join.

Seção 27.2, fig. 27.2 resumida. pthread_join(thread, void **valor): espera a thread terminar e, se o segundo argumento não for NULL, recebe o que ela devolveu. É void ** porque o join precisa escrever no seu ponteiro. Pthread_ com P maiúsculo são os wrappers do livro, que conferem o retorno. Criar e logo dar join é só uma chamada de função mais cara; o normal é criar várias e depois esperar todas.

Nunca devolva algo da pilha

void *mythread(void *arg) {
    myret_t oops;   // na pilha da thread
    oops.x = 1;
    oops.y = 2;
    return (void *) &oops;
}
pilha da threadoops = {1, 2}
pilha liberada???

O ponteiro devolvido aponta para memória que já não é da thread.

Ainda na seção 27.2. A variável oops está na pilha de mythread. Quando a função retorna, essa pilha é liberada; o join entrega um ponteiro para memória que pode ser reaproveitada a qualquer momento. Pode até parecer funcionar, o que é pior. O gcc costuma avisar (-Wall): mais um motivo para ler os warnings. Retorne algo alocado com malloc (slide anterior) ou um valor simples convertido para void *.

Locks

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

Pthread_mutex_lock(&lock);
counter = counter + 1;   // seção crítica
Pthread_mutex_unlock(&lock);

Todo lock precisa ser inicializado (ou com pthread_mutex_init).

Se outra thread tem o lock, quem chama lock espera até ele ser liberado.

lock e unlock também podem falhar: confira o retorno.

Exclusão mútua

Seção 27.3. O contador do simulador, agora protegido. Passo 1: inicialize (estático, com PTHREAD_MUTEX_INITIALIZER, ou em tempo de execução, com pthread_mutex_init, e pthread_mutex_destroy no fim). Passo 2: lock e unlock em volta da seção crítica; só uma thread por vez passa. Passo 3: como quase tudo no UNIX, essas chamadas podem falhar, e a falha silenciosa deixa duas threads entrarem. Por isso os wrappers com P maiúsculo (fig. 27.4). Existem também trylock e timedlock, úteis quando falarmos de deadlock.

Agora é com vocês

Compilar com threads:

gcc -o main main.c -Wall -pthread

Caçar bugs de concorrência:

valgrind --tool=helgrind ./main-race
